# 地牢小径：摘要失败排查与修正

修正已通过 SSH 部署，掌机启动验收通过。部署前后项目 JSON 与卡带哈希均保持一致。

检查对象：game-muq26o90-sywc，74 条消息，已发布第 5 版。最后的菜单/HUD 修改已经保存为草稿，尚未检查或发布。排查未修改原始项目或卡带。

## 原因

应用此前把上下文默认写死为 64,000 token，并将自定义预算上限钳制在 128,000 token，与用户指定的 500,000 token 不符；按旧设置，估算约 48,000 token 就触发自动压缩。

另一个独立限制是摘要输出最多 2,048 token，这是本应用设置的额度，不是 Pi 或模型的上限。项目五次成功摘要的输出依次为 585、985、1,289、1,439、2,004 token，摘要不断累积旧细节，已经逼近旧输出上限。最后两次错误均为“摘要响应不完整或被截断，原始对话已保留”。失败摘要不会写入检查点，因此继续请求反复触发同一段压缩。原始失败响应没有保存 finish_reason/usage，日志无法还原其精确输出量。

## 修改

- 上下文默认 500,000 token，生成输出扩展后预留至少 32,768，估算超过约 467,232 才压缩。模型描述与压缩器使用同一预算；保留可选的小预算配置。
- 摘要默认最多 4,096 token；Pi 拆分回合时可按预留预算更低。仅遇到 length 截断提高额度重试一次，最高 8,192。网络、鉴权或空响应不循环重试；初次请求与重试均可取消。
- 完整历史与拆分回合摘要均要求简体中文、目标 1,200 汉字以内，合并旧信息、删掉过时调试过程，保留当前事实、未完成请求及草稿/检查/发布区别。
- 报错显示明确的输出上限或空响应原因，去掉 Pi 内部英文摘要阶段前缀。残缺摘要不采用，完整记录保留。
- 与更大上下文配套：模型请求体最多 8MiB，项目文件最多 16MiB；模型响应仍最多 1MiB。

## 验证

真实 Pi + 模拟 HTTP 验证：截断后提高额度、只有完整摘要能保存、连续截断仅尝试两次、第二次请求可取消、500k 默认和显式预算都不会被旧 128k 上限裁剪。

只读回放地牢小径的实际 74 条消息与最后检查点：按 500k 预算不再触发这次过早摘要，能继续调用当前源码读取工具。回放不使用付费 API、不发布游戏、不改动原文件；它验证控制流，不替代下一次真实模型生成。完整模型/编辑/素材/流式回归及受限 QuickJS 测试通过。
