**当前问题包括输入节奏、声音编排、逻辑正确性和诊断方式；不能统一归因于 Lua 太慢。** 推箱子已经两次减少绘制工作，但用户仍反馈操作与音乐卡顿。此次在掌机上加载实际安装的 fake-08 核心，测试回放中核心耗时明显低于帧预算；同时复现了按键重复的长间隔、音乐素材自带的静音，以及俄罗斯方块连续重播音效。完整模拟器的显示与音频设备链路仍需要进一步测量。

## 1. 现有测试说明了什么

最新六类真实生成的交付检查为 **6/6**，四次速度/跳跃修改在明确修正判分规则后为 **4/4**。这验证了生成、编辑、语法、发布、资源和有限输入回放，不能当作六个游戏的品质合格率。四次修改的原始 3/4 结果仍保留；一个失败是把代数等价的 `dx*1` 与 `dx` 判成不同修改，重新判分没有重新生成或回放游戏。

本轮在“通过”的平台游戏中确认了额外缺陷：`spr(35,x,112)` 只画一格宽的尖刺，但碰撞用 `hits(64,116,16,4)`，右侧扩展到了精灵之外。将玩家放在 `(74,110)`，实际 fake-08 VM 下一步扣血的断言通过。**能启动并有音频，仍可能在看不到尖刺的位置受伤。** 应增加画面与碰撞范围一致的场景检查。

其他测试结论也要收紧：

- 赛车的 `camera()` 静态提示属于需要核对的警告。本轮阅读实际绘制顺序发现地图、车与检查点在同一镜头下绘制，之后才重置给 HUD，不能把这个警告直接称为摄像机 bug。
- 3D 公告板只按中间射线决定遮挡，宽物体可能露出墙边，仍需逐列遮挡与画面验证。源码地图的格子连通检查表明钥匙在开门前可达、出口在门后；这个结果不证明玩家碰撞半径下能走完整路线。
- 文本评审曾解释“检查、发布、运行成功，所以路径存在”，这是无效推理；另一项速度修改评审返回了错误的 rubric，已保留为评审失败。模型评分不能代替规则断言和试玩。
- 新游戏生成约 219–292 秒，局部修改约 8–10 秒。任务耗时与游戏帧率是不同指标；32MB SSE 与 ARM Agent 一致性测试证明的是宿主传输能力，不证明游戏运行流畅。

原始依据：`build/workshop-eval/runs/live-streaming-fixed/summary.json`、`live-final-native-reassessed/summary.json`；本轮补充断言在 `build/workshop-performance-review-2026-10-02/diagnostics/platform-invisible-spike/`。

## 3. 推箱子：操作停顿与音乐断音分开处理

### 操作节奏已有可复现原因

实际第 3 版第 341–377 行：四方向、撤销、重开都通过 `bp(i) → btnp(i)`。首按立即处理，但后续依赖默认重复；没有移动插值、输入缓冲或专门的长按节拍。

在锁定的 fake-08 VM 中包裹 `moveto` 记录调用，持续按 ↑ 21 个游戏更新，触发帧为 **1、15、16、20**。第一次与第二次相隔 14 帧，约 **467ms**；随后有一次仅隔 1 帧，再隔 4 帧。这会产生“走一下，停很久，然后连走”的体验，不能靠少画几块地砖解决。[官方 btnp 约定](https://www.lexaloffle.com/dl/docs/pico-8_manual.html)也明确存在初始重复等待。

应使用明确的网格输入组件：第一帧执行；长按先等待一个可调的短延迟；之后均匀重复；换方向立即响应，松开清零。可先试 6 帧初始等待、3 帧重复间隔（30Hz，约 200/100ms），再根据用户试玩调整；不能把这个起点当成通用标准。规则坐标立刻结算，动画只推进显示；有动画时最多保留一个下一步请求。O 重开、选关确认用严格上升沿；撤销是否允许长按应明确约定。

第 1 版与第 3 版素材数据一致，替换历史 Lua 后使用同一掌机核心再测：第 1 版全量绘制的核心 P95 为 **1.77ms**，第 3 版局部重绘为 **1.33ms**。优化有收益，但两者都远小于 60Hz 核心 tick 的 16.67ms。不能将“已经减少绘制”写成“已经解决音乐卡顿”。这两次样本不是严格控制负载的基准赛，也没有包含完整前端。

### 断音已经存在于声音素材

第 3 版在初始化和回标题时调用 `music(6,200,3)`；没有逐帧调用音乐。BGM 占声道 0/1，操作音效用 3，当前看不出抢占 BGM 的代码。

但 pattern 6 的 SFX14 音量是 `[3,0,3,0,…]`，SFX15 是 `[2,0,0,0,…]`，speed 都为 16。这是离散短音、带大量休止的编排，不能作为连贯音乐的参考。掌机安装核心在推箱子标题静止的独立回放中，20ms RMS 窗口测到每约 0.26 秒一段 **0.10–0.12 秒数字静音**。无实际音频设备或显示参与，依然断音，说明至少这一部分断续来自素材本身。

这不等于所有规律休止都是 bug，也不能排除用户同时遇到音频欠载。应区分“音频样本中本来就静音”与“设备没按时收到样本”，用参考曲目做对照，再按要求选择连奏、断奏、低音持续或短音反馈；不要擅自消除所有休止。

试听文件：`build/workshop-performance-review-2026-10-02/sokoban-idle.wav`（掌机核心导出，30 秒，不是麦克风录音）。

## 4. 其他游戏中的确定缺陷与潜在风险

**俄罗斯方块：输入与声音连在每帧循环里。** 第 165–166 行长按每帧尝试横移，成功就 `sfx(17,3)`。SFX17 是 BGM 的低音资源之一，speed10、完整32行；拿它作为步进声，在下次移动时重启，会截断声音并产生密集脉冲。实际 VM 诊断：连续左按5帧，播放该音效 **5次**。应实现延迟重复，使用独立短 SFX 槽，按成功动作节拍触发。第 142–176 行没有 ↓ 软降分支，这是修复时的功能回归。

**地牢小径：菜单选项每帧变化。** 第 100–101 行使用 `btn(2/3)`，30Hz 下长按快速穿过选项，既容易选错，也会被理解为控制异常。菜单应首按一次、长按有序重复。该 ROM 没有启动 BGM；只在结束停止音乐。先解决状态与交付差异，不能拿未发布草稿解释正在玩的卡带。

**贪吃蛇：复杂度会随长度增长。** 每次 `draw_board` 扫描 225 格，`resolve_cell` 对每格扫描蛇身；食物生成扫描候选格时又线性检查身体。上限约169节，绘制可达数万次坐标比较。它是增长后的风险，当前30秒回放不能证明长蛇不卡。用二维占用表或整数格 ID 表将查询改成 O(1)，绘制地板后遍历蛇身；移动和吃食物只更新受影响格。无需为了小棋盘预先加入复杂引擎。该项目也没有 BGM 启动调用。

**地窟小肉鸽：3D 数据和绘制单位有问题。** 射线数量32、DDA上限16，已有工作上限；但每帧为所有可见物体新建表，并二次选择排序；`project` 为每个物体重复计算相同视角三角函数。应复用有界工作表、每帧缓存视角基向量、只排序可见对象。`spr(...,sz/8,sz/8)` 是读取更多源精灵格，不是放大同一个图；应按需要用 `sspr`。当前实测没有达到核心预算，列为画面缺陷与扩展风险，不能宣称是本批普遍卡顿的原因。

**塞尔达：规则与资源缺陷优先于微优化。** 既有复盘已定向验证地图与角色使用不同镜头、地牢使用地表碰撞、同一洞口重复领取碎片；末版仍引用未提供的 SFX16–22。没有 BGM 的项目应先修播放连接，不能先调节拍。

**追尾巴的狗：修复过程在猜原因。** 留存 v25–32 连续尝试声道、标题绘制、延音、音量、包络、speed、波形。v26 摘要直接归因“音频缓冲欠载”，但记录没有欠载测量。末版 SFX17/23 等又采用响一行、静音一行、effect0；用户此前明确说“移动流畅，但音乐像被剪掉一半”。这应优先检查实际音符时值与包络，而非继续删绘图或反复改音色。声道3修复是合理方向，但没有整段声音验证就不应称已解决。

## 5. 提示词应如何调整

### P0：核心入口补“诊断与修改证据”

下面这段应加入常驻 Skill，保持短而可执行：

> 用户反馈卡顿时，先区分输入节奏、画面帧间隔、音乐素材断续、音效重触发与运行器问题。读取当前已发布版本及相关循环；不要因为用了三声部、全量重绘或用户说“卡”就认定 CPU 不足。明确列出一个源码证据、待验证的预期变化和需保留的功能；每轮只改变一个主要因素。没有运行数据时只说“调整了什么、请验证什么”，不要声称欠载、性能达标或彻底修复。用户已指出发生位置时直接查，不重复提问。

这条规则要绑定真实差异：改包络需核对提交后的32行音量/effect；改输入需核对首次、长按、换方向、松开；改碰撞需核对绘图与碰撞范围；小改动继续使用 `write_game.edits` 并保留其他玩法与素材。

### P0：grid-turns 提供一个明确的输入片段

当前模块已经讲了落块重复节奏，但推箱子还是裸 `btnp`，俄罗斯方块还是每帧横移。说明“要可靠输入”不足以让模型落实。加入可复用的短组件，例如：

```lua
-- call once per _update; 30hz; initial wait and interval are tunable
hold_dir=-1
hold_ticks=0
function grid_request()
 local d=-1
 for i=0,3 do if btn(i) then d=i break end end
 if d<0 then hold_dir=-1 hold_ticks=0 return -1 end
 if d!=hold_dir then
  hold_dir=d hold_ticks=0 return d
 end
 hold_ticks=min(hold_ticks+1,30000)
 if hold_ticks>=6 and (hold_ticks-6)%3==0 then return d end
 return -1
end
```

这是单方向优先级的示意，支持新方向抢占时需额外记录方向边沿。状态切换、重开及恢复时重置；一次更新只消费一个移动请求，音效接在成功结算之后。动作与渲染插值分开。不要每帧给整局加统一冷却，也不要为修音乐修改角色移动速度。

### P0：音乐仍渐进加载，但加上实际时值与包络核对

核心入口只保留声音连接、单次状态切换、事件音效、声道分工和“有声音不等于声音合格”。详细编排放 `modules/music.md`，避免再次把主线全部变成作曲。

模块需要补充：

- 明确曲目目标是连奏还是断奏，按实际资源核对音符持续行数、休止比例、末尾包络及 pattern 有效长度。用户说半音被剪掉时，不把 `[响,静音]` 等同于延音。
- 移动/菜单音用独立短音效槽、有效长度与适度音量。不能把完整 BGM 低音声部拿来逐步重播。重复事件要限频，命中/失败音应单次结算。
- `music` 只在状态切换时执行；自动空声道与显式音效声道区别清楚；保留给 BGM 的声道也可能被显式 `sfx(n,c)` 抢占。
- 校正当前模块的时间公式。仓库锁定的 fake-08 合成代码采用每 speed 单位183个22,050Hz样本；speed16一行约132.8ms，32行约4.249秒，4行一拍约113 BPM。模块写成1/128秒、4秒、120 BPM，与此运行器不一致。应以运行器测量或实现为依据，并区分近似值；这处误差不是普遍卡顿的根因。
- 附一个短音反馈、一个有持续声部的连贯循环、一个刻意断奏的循环以及社区参考音频，说明适用场景。优先保留许可和来源的社区资料，新增片段只是接口演示，不能冒充社区成品。

### P1：性能、规则与修改回归合在交付核对里

每种玩法提供少量针对性检查：网格占用查表；3D射线/对象有界、复用工作表；摄像机和碰撞单位一致；所有原有按键分支仍存在；胜负、结束与重开可达；音频调用和素材对应。首次开发完成后核对这些具体事实，而不是让模型写一段泛泛“已全面检查”。

在 fake-08 中不能把 `stat(1)` 当真实性能证明：锁定实现固定返回0.5。性能度量应由开发测试环境从原生帧耗时采集；正常 Agent 不具有自动试玩和观察工具，提示词不能虚构这些能力。常驻入口无须增加更多完整游戏例子，场景片段继续渐进加载。

| P1 | 完整掌机前端 | 同一卡带关闭/开启滤镜、倒带与同步设置逐项A/B，记录呈现帧间隔、输入延迟、音频缓冲与欠载；不同时改游戏逻辑 |
| P1 | 参考声音对照 | 同一运行器播放生成曲与保留许可的社区曲；同时保留核心PCM和真实输出录音，区分素材断音与设备断音 |

音频阈值必须有音乐意图：静音比例、相邻样本跳变和能量是诊断信息，不能把“出现休止”自动判失败。核心耗时与16.67ms/33.33ms预算比较只是第一层，全链路预算要在实机前端上记录。给报告分别标注“交付通过”“规则通过”“核心性能样本”“前端/听感待验证”，避免再次让一个6/6掩盖用户体验。
