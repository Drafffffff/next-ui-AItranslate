# 游戏生成器 Harness 优化记录

本轮先解决自动恢复、开启思考和长对话保存的卡顿，再补交付检查。测试使用隔离的 SD 数据副本及本地模拟模型；没有调用真实付费模型，也没有改写用户的游戏。

## 已落实

- 开发与摘要都启用思考并支持 SSE。DeepSeek 发送 `thinking.type=enabled`，百炼发送 `enable_thinking=true`；保留工具调用的实际 `reasoning_content`。Pi 记录 `thinkingLevel=medium`，具体思考深度仍取决于渠道。
- DNS、连接、传输中断、超时及 HTTP 408/429/500/502/503/504 自动重试最多三次，约1/2/4秒退避并加入抖动，用户可按X停止。重发同一请求，失败流的文字、思考和工具参数一起清空，不重复执行已成功的工具。证书、鉴权、参数、容量和主动取消不重试。
- 500,000 token 默认上下文不变；开发输出预算提高至65,536，包含思考。摘要16,384，输出截断时单独提高至32,768再试一次；完整历史不删除。较小的自定义上下文会相应缩小开发输出预算。
- 百炼 Qwen3 使用 `max_completion_tokens` 计算完整输出，摘要另给4,096思考预算。官方文档指出旧 `max_tokens` 在思考模式下限制最终答案，并存在32,768参数上限，因此不能直接给它传65,536。[百炼深度思考文档](https://help.aliyun.com/zh/model-studio/deep-thinking)
- 默认首字及无数据超时120秒，持续SSE总时长最多300秒。配置更短的超时保留。原生错误区分DNS、连接、证书、超时和传输；日志只有状态码、响应字节数和错误类型。
- 压缩后直接投影保留的消息，省去重建全部会话树；已完成消息的token估算缓存并增量更新。模型上下文中的参数校验错误去掉重复完整参数并限长；本地历史和详情仍保留原文。
- 项目保存分为64Ki字符块，帧间让出，再由原生缓冲装配并沿用临时文件、fsync、原子替换协议。UI不拼接或复制整份项目JSON。完成消息的JSON编码用弱引用缓存；队列只持有快照引用，原生装配受16MiB总预算约束，取消或错误释放未提交缓冲。
- 只读工具轨迹由下一次修改或任务结束一起保存；修改工具仍先保存草稿/发布意图，再持久化结果。所有完成的历史、版本、问题、摘要及试玩返回缓存格式兼容。
- 游戏发布成功后最终回复仍先自动重试。全部重试用尽时如实显示“已发布，可试玩”；相同内容再次检查、发布不会创建重复版本。
- `check_game` 使用与fake-08相同的锁定z8lua解析器，只编译不执行，8MiB源码、32MiB解析器内存、3秒子进程预算。字面量声音调用引用空槽或全静音音乐会拒绝；缺少BGM/操作音效、动态编号、摄像机重置给出源码审查提示。
- 新项目脚手架实际播放循环BGM和操作音效。核心Skill要求默认成品包含两者，并明确修复证据、变更回归核对和简短中文回复；作曲细节仍通过独立音乐模块渐进加载。

## 实测方法

使用80,003条消息、10,481,185字节项目的离线副本，包含有效摘要、实际声音资源和单一发布版本。模拟模型完成 `read_game → write_game → check_game → publish_game → 最终回复`，每次完整历史前缀必须保持一致，版本只增加一次。测量从提交修改到任务完成，不含启动和打开项目；模拟模型的耗时不能代表真实云端生成速度。

最长停顿为原生一次QuickJS tick与软件绘制耗时，不含SDL显示提交。宿主峰值RSS不包含语音或解析器子进程。测试未终止用户应用、改CPU频率或清系统缓存，因此是工程压力样本，不能视为稳定的产品延迟承诺。

在同一 `nextui-brick` ARM原生宿主上先跑旧JS，再跑最终JS，各一次，完整历史及发布次数校验均通过：

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 修改至完成 | 44.29秒 | 25.19秒 |
| 最长tick/软件绘制停顿 | 2960ms | 66ms |
| 宿主峰值RSS | 216.5MiB | 141.9MiB |

最长停顿减少约97.8%，总耗时减少约43.1%。长历史可持续显示进度与响应输入，但完整快照持久化仍占不少时间。

参考本机原生结果：旧JS完成同一流程1,852ms、最长停顿170ms；第一版优化869ms/18ms。后续分块保存单次本机测量约932ms/21ms，宿主峰值约142MiB。这里只用于定位瓶颈，掌机结果单列。
