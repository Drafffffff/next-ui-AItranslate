# 游戏生成器真实案例复盘与迭代清单

本次读取掌机上的六个项目，核对完整对话、工具结果、历次源码和实际游戏目录中的卡带。结论是：创建、修改、发布的链路已经成立，新版提问工具也实际生效；当前最影响体验的是游戏逻辑缺陷未被发现、修复缺少事实依据，以及中断后需要用户反复说“继续”。长对话下一步要优化生成与保存路径，不能只优化翻页。

采样于 2026 年 10 月 2 日约 13:30–13:34，设备 `nextui-brick`。只读获取项目与 ROM，没有修改用户游戏、调用付费模型或部署产品改动。最新塞尔达项目后续读取只有 `updatedAt` 变化，对话和游戏内容没有变化。

总计 **270 条消息、31 次用户输入、105 次工具调用、18 次成功发布**。工具调用中有 7 次失败：5 次写入失败、2 次发布前检查失效。另有 6 次模型请求错误和 3 次主动取消；模型请求错误包括旧轮数/摘要限制，不能全部归因于网络。

所有六个 ROM 的 Lua 都与其最后一次已发布版本相符；五个项目的草稿 Lua 也与发布版本相符，地牢小径除外。这说明唯一产物管理基本可靠，但“已保存”与“已可试玩”的区别还需要产品明确显示。

四个项目出现了用户对操作、核心机制或品质的负面反馈。另两个没有充分的试玩反馈，不能据此认定可玩或满意。样本很小、模型和宿主版本混杂，不做模型排名或成功率外推。

## 当前流程在哪些地方失效

### 关键玩法提问已生效，但没有贯穿后续交付

最新塞尔达案例先读取脚手架，再询问“单屏房间”还是“大地图滚屏”。用户真实选择大地图，Agent 随后加载 `gameplay-design` 和 `api`，生成、检查、发布。这一段符合预期，值得保留。

问题出在后半段：选择结果没有变成可持续核对的设计记录。Agent 把“大地图、三处洞穴、地牢、敌人”写进了说明，却没有持续核对各项是否完整实现。首次发布源码已经缺少地表敌人的生成；洞穴只是现场生成碎片，没有独立探索内容。可以选择小规模玩法，但应准确说明简化后的规则。

需要记录这个游戏的核心循环、操作、目标、场景坐标、音乐安排和本轮修改边界。记录应很短，每次从实际代码与真实用户选择更新，不能保存模型自称成功的推断来替代事实。

### 格式通过距离可交付仍然很远

当前 `check_game` 检查入口、允许接口和素材数据格式，不解析完整 Lua、不验证规则，也没有检查 Lua 中的音效编号是否有对应资源。工具描述中的“references”容易让模型高估它的能力。

本次使用锁定的 z8lua 解析器，单独加载了六个当前草稿及十九个历史版本，共 **25 份 Lua，语法全部通过**。这进一步说明，单加语法检查有价值，但无法解决本批案例的主要逻辑问题。

几个具体缺陷：

- **塞尔达摄像机**：`draw_world()` 用滚动摄像机画地图，函数末尾立即 `camera()`；随后角色、碎片、敌人与剑击按世界坐标绘制。角色初始世界位置为 `(104,96)`，地图摄像机约 `(44,36)`，角色应在屏幕约 `(60,60)`，却以默认摄像机画在 `(104,96)`。第 2 版所谓摄像机修正 `player.x+3-63` 与原来的 `player.x-60` 在代数上完全相同；第 3 版仍保留重置顺序。
- **塞尔达地牢**：地牢画的是独立满屏地板，移动仍调用地表 `map` 的 `blocked()`。例如 `(32,48)` 对应地表湖泊，在地牢成为看不见的障碍。
- **塞尔达目标**：每次在同一洞口按 O 都能创建新碎片，没有已领取标记；可以重复领取，削弱三处探索目标。地表敌人数组重置为空后没有生成路径。
- **塞尔达声音**：源码调用 SFX 16–22，但项目音频只提供 0–5、8–15，七个调用落到未提供的槽位；也没有启动 BGM。保存音频数组不等于游戏会播放声音。
- **赛车计圈**：通过目标线的条件要求 `py` 从小于 120 跨到至少 120；此时车的采样点进入第 16 行的边界墙，移动立即回滚，目标线不能按该规则触发。第 2 版仅修改操作没有修到这里。
- **俄罗斯方块回归**：第 4 版 `_update()` 没有读取 ↓ 的 `btn(3)`，之前存在的软降丢失；左右移动改为每帧重复，缺少明确的首次延迟和重复间隔。末版场地边框仍把 `rect` 的右下坐标误当宽高使用。
- **第一人称素材**：地窟小肉鸽用 `spr(...,sz/8,sz/8)` 尝试把单格图像放大；这实际选择更多源精灵格，应使用适合目标尺寸的 `sspr` 或明确的绘制方法。地图初始化封闭边界后，随机“开路”还可能把边界格重新打开。

除了源码审查，还用实际 z8lua 定点数解释器和模拟图形/输入接口，定向复现了塞尔达摄像机重置、空地表敌人、重复碎片、地牢隐形碰撞、俄罗斯方块无软降、赛车目标线移动回滚。这是开发诊断，**没有实机渲染或完整自动试玩，不证明视觉、难度或性能达标**。

### 修复常从解释开始，缺少可核查的原因

地牢小径先把射击不受控归因于未保存朝向，用户再次反馈后才查到 P8 `atan2` 参数问题。塞尔达则把地图错位归因于碰撞采样范围和镜头中心，遗漏了绘制时摄像机提前重置；还声称“四角采样不再多算底下一行”，实际却把下沿从 `+6` 扩大到 `+7`。

这些不是工具执行失败，而是诊断与验收薄弱。修复应先说明源码中的证据、预期变化和其他可能原因，修改后对照实际 diff；证据不足时说“怀疑”，不要先宣称“找到真正原因”。“不能玩”或“文本过长”这样的反馈，先用一个简短问题确认是启动失败、按键无效、游戏机制还是工坊界面，避免修改错误层。

### 发布与恢复依赖下一次模型请求

最新案例出现两种不同的中断：

1. 草稿写入并检查成功，但下一次模型请求失败，尚未发布。用户说“继续”后，Agent 直接发布，却因检查凭据只在本轮内存中有效而失败；随后重新读取、检查、发布。
2. 第 2 版已成功发布，下一次生成结束说明的请求失败。界面以网络错误结束，用户又说“继续”，Agent 才补充说明。

保留当前草稿的安全约束是正确的，但需要宿主提供明确的运行阶段和恢复路线。不能因为最后一段模型文案失败，把已发布版本显示成整体失败；也不应自动重复发布产生新版本。网络错误现在把大量 curl 失败归为“检查 Wi-Fi”，这不足以定位是 DNS、连接、证书、传输中断还是服务端问题。

### 小修能编辑，大修仍容易整包重发

28 次 `write_game` 中，13 次传完整 Lua、13 次传 edits、2 次只更新素材。局部编辑已经有真实用途，不需要再造第二个编辑工具。

最新塞尔达美术重制第一次因为一个精灵像素行只有 7 个字符被拒，下一次仍重发整份约 8.9 KB 的 Lua 和所有精灵。首轮 ASCII 失败也重发完整代码。其项目最终单次请求输入已到 **44,547 token**，累计报告输入 **515,813 token**；这是多次调用的累计量，不是一次达到 50 万上下文。缓存命中已经包含在输入中，不能再相加。

当前 schema 失败会把 `Received arguments` 全部带回模型。塞尔达失败结果占约 14 KB，俄罗斯方块约 16 KB，包含重复代码或音符。UI 折叠错误只改善显示，模型上下文和磁盘仍保留全文。应把完整参数留作历史详情，给模型返回字段路径、期望、实际值与“未写入”的简短错误。

### 对话没有很好地服从掌机的阅读成本

核心 Skill 已要求中文、1–3 句，但最新版仍多次英文播报，再输出长篇改动说明和多个试玩问题。塞尔达发布回复分别约 400–650 字符，占多页。很多技术细节适合 SE 详情，不适合默认屏幕。

生成代码属于工具参数，通常没有可展示的文本增量；所以“已支持流式”并不意味着整段写代码期间都有可读文字。需要从 `toolcall_delta` 提供可信的状态，例如“正在生成源码，已收到 N 字符”，完整后才显示保存结果。不要输出未验证的完成百分比。

## 1 GB 内存与长对话策略

实际读取：`MemTotal=998332 KiB`，约 975 MiB；`MemAvailable=750944 KiB`，约 **733 MiB**；无 swap。工坊本体当前 RSS 约 **39.5 MiB**，本次进程最高 RSS 约 42.2 MiB；语音进程约 **5 MiB**。语音进程 VSZ 约 1.2 GiB 是虚拟地址空间，不能当作真实 RAM 占用。

当前内存余量足够支持更积极的缓存和较大历史预算。已有 Brick 压力测试在 80,003 条消息、约 10.7 MiB 项目下，峰值 RSS 约 102 MiB，暖缓存翻页平均 30.4 ms，首次打开 2.1 秒。这个测试主要验证浏览，未覆盖大历史下连续生成、写入、摘要、语音和头像并发。

仍需优先解决的源码路径：

- `saveProject()` 在 JS 线程完整 `JSON.stringify(p)`；每个消息结束与工具结束都可能再保存整个项目。原生写盘异步不消除前面的同步序列化开销，保存队列还能同时持有多份快照字符串。
- 每次模型调用重新构造完整会话树、投影、估算和请求 JSON；压缩之后仍遍历完整历史。部分 `indexOf` 操作在长历史投影中还会放大扫描成本。
- 大型工具错误、旧完整代码、素材数组重复进入上下文；这既消耗请求时间，也增加解析与复制内存。
- 现有渲染已经增量索引、仅排版可见窗口，继续优化应优先命中生成与保存链路，而不是重新实现整套文本排版。

**建议的第一轮预算，均为待验证的目标：**

| 项目 | 建议 |
| --- | --- |
| 模型上下文 | 保留用户指定的 500,000 token；常规修改按当前源码、设计记录和近期反馈构建上下文。清理重复工具回显属于上下文组织，不减少模型窗口或丢弃原始历史。 |
| 生成输出 | 保留当前 32,768 token，允许复杂游戏有足够输出；局部修复通过 edits 减少不必要的完整重写。 |
| RAM | 允许工坊及子进程合计向 256–384 MiB 使用；到 512 MiB 量级必须经过并发压力测试并根据 `MemAvailable` 动态降级，不能当作可直接硬编码的保证。 |
| 内存水位 | 建议剩余可用低于 192 MiB 时回收缓存、限制预加载；低于 128 MiB 时阻止新的大型分配并给出可恢复状态。避免临近 OOM 才处理。阈值需实测校准。 |
| 缓存 | 优先缓存会话投影、token 估算、项目索引和相邻页面；首轮总软预算可试 32–64 MiB。增大缓存不能替代增量算法。 |
| 历史存储 | 改为追加事件日志加定期快照，代码和素材版本按内容引用；完整历史长期保存，打开只读索引和近期内容。完成迁移与实测后再扩大当前 16 MiB 项目上限。 |
| 请求预算 | 区分连接、首包、流式空闲、总时限；长响应有持续进展时允许更久。摘要当前另有 60 秒上限，应纳入统一配置与耗时观测。 |

不能承诺 1 GB 下永不溢出：必须测量生成过程中 C 缓冲、JS 对象、UTF-8 字符串、图集与语音的同时峰值。希望更激进的方向是充分利用可用内存维持交互与完整数据，而不是无条件放大所有缓冲。

## 按优先级排序的迭代清单

| 优先级 | 迭代项 | 具体改动与验收依据 |
| --- | --- | --- |
| P0 | 长对话生成与保存性能 | 增量上下文树与估算、合并待保存快照、历史追加写入，移出大块同步序列化；在 10 / 30 / 60 MiB 历史下实际跑生成、编辑、发布、摘要及语音组合。目标：暖翻页 P95 小于 50 ms，操作响应 P95 小于 100 ms，大工作分批或放原生后台，记录最长停顿、RSS/HWM、MemAvailable；任何取消/断电恢复不能丢已确认的写入。较大容量是新测试目标。 |
| P0 | 发布与错误状态恢复 | 宿主记录“生成中、草稿已存、已检查、已发布、待回复”；保存检查的内容哈希与校验器版本，恢复时核对；已发布后回复失败仍显示已发布并可 SR 试玩。重试最多补缺失阶段，同一操作不重复加版本，X 取消不自动重试。重放塞尔达两处中断验收。 |
| P0 | 交付检查与修复证据 | 现有 `check_game` 增加实际 Lua 语法、静态资源引用、常见 API 使用诊断，分清错误和无法判断的警告；增加模型提交前的短审查步骤：坐标/摄像机、输入可达、胜负可达、状态切换、重开、资源保留。用本批坐标、计圈、软降、空音效缺陷建立开发回归样例。保持工具能力说明真实；不假称自动试玩。 |
| P1 | 每个游戏的短设计记录 | 持久化核心动作、目标、风险、操控、场景、视听安排和未完成项；本轮记录必须保留的行为，例如软降或射击方向。需求明确直接开发，只在关键分歧时提问。塞尔达选择能跨中断保留，俄罗斯方块重构不遗漏软降。 |
| P1 | 首版品质基线 | 建立可复用的输入/重复节奏、世界摄像机、场景碰撞、HUD 与状态组件或片段，扩充社区来源的相应范例；首版包含清楚目标、角色可辨识、合适反馈、完整结束/重开，按游戏安排音乐和事件音效。避免用户先投诉才补声音或美术；音乐继续作为渐进模块，不占据全部 Skill。 |
| P1 | 诊断与修复流程 | 用户反馈先定位发生层；每次修复对照源码证据和实际 diff，明确待试玩验证点，禁止无依据“已彻底修复”。美术修改优先素材 patch，机制修复优先 edits；涉及范围广再整段重构，并核对已有规则。对“显示文本过长”不再默认改游戏。 |
| P1 | 工具错误与上下文去重 | schema 错误给模型返回字段路径、实际值和简短修复要求；完整参数保留详情。对过时 `read_game` 和全量资源回显做确定性投影去重，保留工具配对与当前真实源码，摘要继续保留原始历史。把塞尔达单行精灵错误的修复成本明显降低，并记录减少的请求字节/token。 |
| P1 | 掌机会话呈现 | 中文播报和短完成说明；宿主固定显示最新发布版本、草稿有改动、可试玩状态，技术细节留 SE。代码流式阶段显示收到的源码量和活动时间；保留全部操作可查。发布后的默认说明控制在一屏内。 |
| P1 | 实际运行观测 | 记录宿主/Skill/模型版本、请求起止、首 token、空闲中断、工具耗时、错误类型、重试次数、摘要原因、请求 token/字节、帧停顿与内存峰值；只记录必要诊断，不记录密钥。下一次复盘能区分模型慢、网络断、UI卡、保存慢，能按同一版本比较。 |
| P2 | 发布版本回退 | 已有最近八个版本，补用户可达的恢复操作，恢复到同一游戏入口；显示简短实际变更摘要。旧卡带可玩时，未完成草稿不会覆盖它；大重构失败可以恢复最近可用产物。 |
