# PICO-8 小型 3D：实现选择和数值边界

PICO-8 没有宿主提供的 3D 引擎或模型导入工具，3D 画面由 Lua 计算并用现有图形 API 绘制。用户要求 3D 时保留这个需求，不静默降成俯视 2D。

## 按玩法选方法

| 需求 | 方法与参考 |
| --- | --- |
| 第一人称迷宫、探索、简单 FPS | 2.5D DDA raycaster：二维格子地图＋垂直墙柱，参考社区 M2tias 的 raycaster 和适配 `raycaster.lua` |
| 真正的空间立方体、飞行、隧道、低多边形 | 摄像机坐标 → 近裁剪 → 透视投影 → 深度顺序，参考 freds72 的真实多边形渲染原作，以及 `mesh3d.lua` 的真实三维顶点与线框 |
| 3D 赛车或道路透视 | 先明确是投影式道路还是空间多边形；曲率、道路宽度和缩放用有界参数，世界距离不无限增长 |
| 仅“做一个 3D 游戏” | 可采用小型第一人称迷宫并说明实现方向；只有方法差异会改变用户目标时才询问 |

线框、实体多边形和 raycaster 是不同方法。线框示例没有面遮挡，不应说已实现实体模型；raycaster 的墙从二维地图生成，不应说它能表现任意三维地形。

## DDA 与第一人称移动

- 相机方向 `dir` 与垂直相机平面 `plane` 生成 `ray=dir+plane*camera_x`。DDA 距离是投影方向的深度；不要再给这种深度额外乘一次余弦。若使用角度步进射线的路径距离，则需转换为垂直深度以避免鱼眼。
- 网格地图存在 Lua 数组里；不能把社区原卡带的 `mget/fget` 结果、地图、旗标、门、纹理或音乐当作当前项目数据。
- 接近轴线的方向分量不能直接除零或使用巨大哨兵。示例把分母幅值限制到 0.005、DDA 步数限制到 16，并把地图外视为墙；更大地图需要重新推导距离上限。
- 位置与射线用同一坐标单位。玩家有半径，分离 x/y 移动并检查四角，避免斜向穿墙。画面的墙深度不是角色碰撞距离。
- 初始配置可采用 32 条射线、每条 4 像素列宽；分辨率和 DDA 上限是可调起点，不是已测得的 Brick 性能保证。先做实色墙，纹理和 billboard 必须基于实际素材并限定数量。
- 加入终点、操作提示和重开，不能仅交付可以转动的走廊截图。终点从起点连通；小地图与目标提示让目标可定位。

## 三维投影、裁剪和遮挡

Billboard屏幕裁剪不能改变纹理坐标的来源。先保存完整投影左右界 `left/right`，再夹出可见 `c0/c1`；每个可见列仍按 `(c-left+.5)/(right-left+1)` 取源列，不按裁剪后的宽度从纹理0重新开始。否则半个物体移出屏幕时，剩余半个会被拉成整张纹理。核对左右两侧部分出屏、完全出屏和墙遮挡分别处理；分母为正才采样，源列夹到0..7。

- 保持小范围世界坐标。变换到相机坐标后，透视是 `sx=cx+x*f/z`、`sy=cy-y*f/z`；P8 `sin/cos` 接受圈数而非弧度。旋转使用原 x/y/z 的临时变量，避免就地修改前一个分量后污染下一个分量。
- 在除以 z 前处理近裁剪，例如 near=0.2。一条边跨越近面时计算交点；都在近面的相机一侧（z<near）就剔除。不能把负 z 或零 z 直接投影后再夹屏幕坐标来掩盖问题。
- 几何、可见面和对象量有硬上限。线框示例限制 6 个立方体，每个 8 顶点、12 边。增加内容时减少分配和绘制，不能把这些数值说成任意规模都流畅。
- 实心多边形需要背面剔除和合适的远到近顺序；P8 常用子集没有现成 `triangle()`，必须提供有界扫描线填充函数，不能虚构图形 API。Painter 排序不等于完整 z-buffer，交叉面可能仍需拆分。
- HUD 画在恢复 `camera/clip/pal/palt` 之后；屏幕抖动不能改变世界碰撞。线框示例的深度顺序依赖所有立方体同速前进、按远端生成；速度不同或可倒退时要重新排序。
- 视觉与碰撞可以使用不同表示，但要一致：隧道立方体投影是三维图形，撞击使用接近摄像机平面时的世界空间距离。不能用屏幕上的近大远小框直接扣生命。

社区原作、固定提交、许可和本地保存位置见 `assets/community/sources.json` 与 [社区来源与采用记录](../references/community.md)。原作可能包含当前工坊禁止的内存操作、模型解包和额外素材；借鉴算法时适配，不直接提交原卡带全文。

## 掌机库中的真实案例

- Wolfenstein 3D 的 `drawwalls` 使用方向＋相机平面，保存墙深度；`drawobjects` 变换物体到相机空间并与墙距离比较。借鉴同一深度体系，工坊billboard应按其覆盖列与z-buffer比较，不能画在墙上。原作仅按物体中心列判遮挡是它的近似，较宽精灵逐列遮挡更可靠。
- Hungry Harry 3D 的 `draw_world_all` 按nearplane/farplane与横向可视范围遍历tile世界，再计算透视尺寸；这是有界透视图形，不是通用任意模型引擎。先裁剪世界候选，再投影，不能为了画一个小房间每帧遍历无限世界。
- Pico Off Road 的车辆物理、waypoint与比赛状态独立于3D绘制。投影可工作仍不代表赛车可玩，操作、边界碰撞、圈数和完成条件要结合 `racing-physics`。

源码位置与版本见 `references/library-cases.json`，研究不附带原作纹理、地图或内存资源。可用的纹理必须来自当前精灵表；`sspr`目的宽高是像素而`spr`宽高是8×8格数，两者不能互换。核对轴向视角、近面、身后物体、墙后奖励和重开，不宣称未发生的视觉/性能测试。


## 扩展前检查每帧工作量

每帧一次计算视角sin/cos与相机平面，投影所有对象复用它们。可见对象先裁剪再进入有界工作表，复用记录和z-buffer，避免为每个候选新建table；排序只处理可见对象。保持射线、DDA、公告板和粒子上限。更细纹理按实际核心耗时逐步增加；不要因为当前32列可用就宣称任意规模流畅。billboard逐覆盖列比较同一深度体系，画大精灵时只用中心列遮挡可能露出墙边。`spr`源格数不用于目标放大，缩放应核对`sspr`目的像素尺寸。


## 分阶段保存，避免长推演没有产物

复杂新建先确定小地图、射线墙、输入/重开与音乐，及时write_game保存一份包含三个入口且能解析的Lua；随后以edits添加钥匙/门/物品/危险和裁剪反馈。每个阶段保持完整草稿，最终需求齐备后检查并发布；不把中间阶段当成已完成游戏。不要一次推演整个大系统直到耗尽输出预算。读取完整示例后选取必要结构，不同时重写渲染、关卡、绘图素材和编曲。

## 对象与绘制字段必须一致

进入同一个drawobj列表的钥匙、门、怪物都要在reset时初始化绘制读取的size、yc、spr，不能只给静态物品这些字段。逐对象推演首次可见、追逐放大、被收集隐藏和重开；解析通过不能发现nil算术。以对象实际spr计算纹理源坐标：sx=(spr%16)*8，sy=flr(spr/16)*8；逐列sspr用sx+u、sy，不能所有对象读取精灵0的同一列。屏幕裁剪保持完整投影范围计算u，同时将实际目的列限制在0..127；大对象在左右边缘仍须正确纹理和深度。
