# 网格、回合与益智：一次行动是一次事务

依据：Porklike `passturn/moveplayer`，Guncho `update_game/handle_player_move/player_nope`，Woodworm `save_state/undo/reset_level`，Pico Tetris `handle_das/legal_pos/rotate_curtet`，High Stakes `update_game/dealround`，Mai-Chan's Sweet Buns `checkorder/neworder`。源码位置见研究清单。

## 输入节奏：首按立即、重复均匀

裸 `btnp` 有默认初始等待；`btn` 每帧提交则会穿过菜单或快速滑到底。不要用少画地砖修长按停顿，也不要加一个全局冷却锁住所有操作。本模块末尾附 `assets/snippets/grid-input.lua`，它是本工坊的可调输入组件，社区方法仍以开头列出的来源为准。

每个 `_update` 调用一次 `grid_request(6,3)`，返回0..3方向或-1。30Hz下6帧初始等待约200ms，随后3帧约100ms；这是调参起点，已有用户认可的节奏优先保留。首次方向、新方向按下立即提交；松开重置，相反方向同时按互相取消，其他轴仍可用。同一采样出现多个新方向时优先较小编号；已有方向按住时新的有效方向抢占。计数是短周期倒计时，不用无限增长的帧数，采样不创建临时table。

进入新关/重开时 `grid_input_reset()`；菜单与游玩每帧采集，确认、重开等按钮另外用严格上升沿。只消费一次方向请求，成功动作后才更新步数和播放短音效。动画用显示坐标插值，规则立刻结算；动画期间至多保留一个下一步请求，状态转换时清掉它。没有动画时直接提交，不人为增加响应等待。

核对首按、长按、松开再按、换方向、相反键、菜单切换、O长按重开与撤销边界；长按重复频率和音乐tempo是独立参数。

## 网格规则和画面分开

格子像素尺寸用 `tile_size`，棋盘查询用 `tile_at(x,y)` 等不同名称；不要先 `cell=12` 再声明 `function cell()`，函数会覆盖数值，绘图第一帧的乘法就报错。检查全局常量/数据表/函数同名覆盖，并核对所有绘制读取的实际类型。

用格坐标存棋盘、实体和目标，用渲染插值画动画。是否允许动作由棋盘决定，不能用正在缓动的像素位置判断格子是否空。规则在 `_update` 执行，`_draw` 不扣回合、不修改棋盘。

回合实现可采用 `await_input → resolving_player → resolving_enemies → settle → await_input`。先检查动作合法性；成功才更新玩家/物件状态、增加turn_id、运行一次敌人决策；动画帧只推进表现。Porklike/Guncho会对非法动作给反馈而不推进正常敌人回合。用户设计“撞墙也消耗回合”时则明确采用该规则，别暗自改变。

动画期间禁止重复提交，或只保留一个下一步输入；恢复时清理缓冲。行动结算后检查胜负与换关，再接受输入。敌人冷却按已提交的回合递减，不能每个动画帧递减。方格/六角格邻接规则不同，Guncho的格子结构不能直接当作四方向棋盘。

## 撤销和重开

Woodworm除了角色位置，还恢复修改过的砖块和方向，并清空下落/动画残留。工坊的小棋盘可用有界完整快照，更容易确保一致：合法动作前保存棋盘深拷贝、箱子/蛇身等实体位置、目标/开关、步数和当前关卡规则状态；提交失败不压栈。不能只复制外层table，内部数组仍共享会破坏历史。

撤销恢复一个稳定状态，清掉动作队列、重力/移动动画和胜利过渡。历史上限按棋盘大小选择，例如32步作为起点；无历史时反馈而不报错。重开从不可变初始布局重建状态，不能用已改变的数组当初始地图。不会撤销的游戏不必为了参考硬加撤销。

推箱子先检查箱子后方，全部目标匹配才胜利；目标层不被箱子/玩家覆盖后删除。初版手工设计可解关卡，有意展示一种新规律。随机墙+箱子+目标不等于可解谜题；只检查连通不能证明箱子可推到目标。

## 落块：输入与合法位置

Pico Tetris把横移延迟重复、纵向软降、旋转踢墙和锁定分开管理。工坊保留这些职责：

- 横移首次按立即一格，按住一段延迟后以独立节拍重复；松开或换方向重置。左右同时按采用明确规则，不产生随机方向。
- 软降首按在当前更新立即下一格，按住再用独立的短周期倒计时重复；松开清掉软降计时。不能只改重力计时到期后的重置值：旧的长重力等待仍会让首按卡住。若共用下落计时，按下时必须立即截断旧等待、松开恢复重力节拍。同帧重力与软降最多结算一次下落/锁定；旋转重构仍保留软降路径。
- 旋转、硬降、开始和重开用严格上升沿，每帧记录 O/X 前态。不要用裸 `btnp` 造成长按反复旋转或连续锁定新方块；从标题进入游玩时仍按住 O 也不算第二次按下。若玩法明确要自动连旋才另外设计重复节拍。
- 候选移动/旋转先生成候选方块，用统一legal函数检查边界和占用，合法才提交。踢墙尝试有序且有限，全部失败恢复原位置/朝向。不能只把超界方块夹到边界。
- 落地后的锁定延迟有明确上限，旋转续期也有限；生成区堵塞判失败。清行从底向上压实，不能跳过连续行。
- 原作有旋转系统并不意味着用户要完整竞技规格；简化规则要明确、保持输入可靠。

## 让益智有信息和取舍

High Stakes发牌时生成可观察线索，并在动作动画/结算中锁定操作；不只是随机翻牌惩罚。Mai-Chan根据实际订单匹配结算、替换订单，并限制同时在场的订单数量。借鉴这两点：玩家在行动前应能看到会影响选择的信息，成功/无效的反馈应对应真实规则。

原型应先定义可见状态、隐藏信息、合法操作、成本/收益和终局条件。例如订单匹配要比较完整组合，失败是否消耗步数由玩法决定；不能只检查碰到了一个物件。有限牌组应移除已抽条目，空牌组有结束/补充规则；随机选择有界，不能无限重抽等待条件满足。

## 源码推演的关键场景

非法移动不改棋盘/回合；一次合法输入在整个动画里只结算一次；移动+环境改变后撤销完整恢复；连续撤销到初始状态不越界；结束页长按不会跳过重开；连续两行同时清除；墙边旋转失败回到原状态；长按软降始终走得到代码分支；订单不匹配不误发奖励。只检查该游戏具有的机制，不虚构自动试玩结果。
