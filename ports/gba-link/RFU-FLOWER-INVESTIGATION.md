# 花屏定位与修复工作

状态：已找到 IME 中断寄存器语义错误，修复通过独立 IRQ 前后对照测试；网球长时间对照与掌机更新验收正在进行。

## 现场

2026-10-07 `.91` 的软件 framebuffer 花屏、`.70` 球场正常，两端仍显示 15–0。客机仍收取网络数据和 ACK，但游戏 uplink 与核心网络轮询停止。两次间隔约 73 秒的非原子进程内存快照，RFU 持续等待 `0x25` 命令的参数（5 words 仅完成 2 words）；PC 数组位于 `0x0801D694`，对应游戏的串口等待循环。联机库指针 `0x020033F0` 为零，BG0CNT 为零。未观察到 SPI 超长命令保护触发。

这些是故障后的状态，缺少异常前的第一次写入。不能仅凭它们判断指针和显示寄存器谁先损坏，也不能证明 ARM64 动态编译或暂停是根因。

## 定位版

保留现有 RFU 协议与等待策略，只为 BTME 游戏且 RFU 已处于主/客状态时启用有限诊断：

- 监视 CPU 与 DMA 向联机库指针所在四字节的写入，以及 BG0CNT 的变化，记录 PC、旧/新值、写入宽度和 RFU 命令进度。相同值不记录，每次适配器 reset 后最多 256 条。
- ARM64 的 STR/STRB/STRH 与 STM 对该四字节的写入走既有 C 写内存路径，确保也能捕获动态编译的写入。该小范围分支不修改写入值；四类指令已加入 homebrew 对战 ROM 的读回检查。
- 保存最近 64 次 SPI 传输。联机库指针被写零，或参数接收状态连续 180 个运行帧不推进时，最多输出一次轨迹。GPIO reset 清空诊断计数；不会强行重置游戏或修补 guest 内存。
- `source=1` 表示 DMA 写 EWRAM；`source=0` 是 CPU 内存或 IO 写入口。IO 入口也可能由 DMA 调用，不能仅凭该标记把 IO 写归为 CPU 指令。

诊断改变了部分内存写入的执行路径，可能影响性能与复现概率；未测真实掌机影响前不称零开销。不会自动关闭动态编译作为永久方案。

## 本地与 ARM 对照

测试 runner 增加无 SDL 的 PPM 截图，以及可指定游戏帧的前端暂停/恢复，用于在固定 ARM64 SDK 同时运行 JIT 与解释器。它模拟生产网络暂停协议，但不覆盖 NextUI 菜单的完整图形资源生命周期。商业 ROM 和存档始终在私有忽略目录中。

后续根据首次异常写入的指令和 SPI 序列修正状态机、IRQ 或执行逻辑，再做可重复回归。验收仍需两台掌机完成比赛、反复菜单返回及持续运行；定位版部署不等于花屏修复完成。

## Mac 上的 ARM64 复现（2026-10-07）

固定 SDK 内的两个实际 ARM64 JIT 核心复现了球场背景损坏：RFU child 停在 `0x25` 参数 2/5，PC `0x0801D694`、BG0CNT=0、库指针变为 `0x11`，未触发超长 SPI 保护。对应软件截图与日志已保存在忽略目录 `flower-fix/arm-flower-reproduced`。解释器对照组完成 30,000 帧并持续交换游戏数据，截图显示正常球场与计分。解释器二进制使用较早诊断门控，不能将此对照单独视为已确认 JIT 根因。

第一版的背景变化消耗了共享 256 条日志额度，未记录到关键指针写入。正在将指针与背景分别计数，并捕获指针变为非 RAM 地址（包括 `0x11`）的首次变化，再以同一操作序列重跑。定位版 326bb9dc 已在两台空闲掌机安装并校验；它仍不是修复版。

## 首次破坏与根因

额外队列追踪版（仅本地，未部署）捕获到同一发送队列重复进入：`0x0801B078` 两次把剩余长度设为 8，中间没有新的应用消息入队；第二次调用先复制 8 字节并将剩余长度清零，第一次恢复后从 `0x0801B01E` 启动长度为零的 DMA3。DMA3 按其既定语义将零扩展为 65,536 个半字，从 `0x0200197C` 复制到 `0x0200208E`，覆盖联机库指针等内存。大范围 DMA 之前 BG0CNT 仍为 `0xC407`，指针仍为 `0x02001FB8`；之后监视到指针两个半字被先后写零。证据保存在忽略目录 `flower-fix/jit-v4-reentrant`，商业 ROM 内容不打包。

消息处理函数在 `0x0801AF66` 用 `strh r0,[r0]` 向 IME (`0x04000208`) 写入地址的低半字 `0x0208`，用最低位为零关闭中断。gpSP 原实现完整保存该值，并将任何非零 IME 判断为允许 IRQ，导致本应关闭中断的消息队列临界区仍可被串口 IRQ 再次进入。它并非只存在于 ARM64 JIT；解释器的独立测试也稳定暴露了错误，JIT 的不同执行时机使网球故障更容易出现。

修复将 IME 写入限制为 `value & 1`，并将 CPU 的两个 IRQ 判断都限定为最低位（兼容旧状态中可能保留的高位）。与 [mGBA 的 IME 写入实现](https://github.com/mgba-emu/mgba/blob/master/src/gba/io.c) 一致。保留已有联机等待策略与 DMA 语义，没有修改游戏 ROM、强行修复游戏 RAM 或关闭 JIT。额外发送队列追踪与其中间 STM PC 诊断改动不进入修复包；生产版仅保留有限关键指针诊断、增加大范围 DMA 故障记录。

## 独立回归

`tests/ime-probe.S` 是原创测试 ROM，通过真实 Timer0 IRQ 验证：IME 写入 `0x0208` 后中断保持关闭且 IF 可积累；写入 `0x0209` 后恰好执行一次 IRQ；字节和 32 位写入也只保留最低位。旧核心在 Mac 解释器及 ARM64 解释器/JIT 均失败（临界区出现 IRQ，IME 读回 `0x0208`），修复核心均通过（IME 读回 0，随后允许正常 IRQ）。运行入口为 `python3 ports/gba-link/tests/run-ime.py`；`--arm` 验证固定 SDK，`--core ... --expect-fail` 保留旧核心负对照。

正在让旧、新两个 ARM64 JIT 对战组用同一初始存档与操作序列运行 40,000 帧，包含前端暂停恢复。此前旧核心三次本地出现同类大范围 DMA；修复的网球与真实掌机结果将单独记录，不以独立 IRQ 测试代替真实游戏验收。一次本地硬件断点试验设置报告资源错误后仍产生调试陷阱，导致该回合测试进程停止；其运行终止不能当作游戏自然崩溃证据，之后复现均不使用断点。
