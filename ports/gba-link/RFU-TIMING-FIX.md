# RFU 网络等待时序与数据保护

2026-10-07 的双 Brick 比赛日志在约 31 秒内新增 985 次未及时确认，但大多数交换最终收到确认。前端约 60 FPS 并不代表游戏更新流畅；`host_no_reply` 也不是 IP 丢包率。此次候选继续使用可靠有序 TCP，不改变 RFU 包格式。

## 实现

原有虚拟 CPU 周期倒计时保留；主机缺少确认时，重试期限还必须达到单调时钟计算的真实等待期限，至少 33334 微秒（两个 60Hz 帧）。游戏配置的较长重试期限和总等待期限继续适用；有限客机等待也同时检查真实时间。已收到所有实际连接客机的确认则立即成功。配置为零仍表示无限等待。未支持单调时钟的平台保留原周期期限。

这是针对异步模拟器/网络的时序适配，改变了模拟 RFU 的最短失败等待时间；不声称严格复刻真实无线硬件。没有新增 sleep 或阻塞网络读取，也不延长前端空轮询退避。持续拥塞仍可超时，且真实时钟包含暂停时间；恢复时先处理已有网络数据，掌机菜单暂停/恢复仍须复测。

零字节交换会产生事件，但不再清掉尚未被游戏读取的非空 mailbox。后来的非空负载仍替换旧负载，不能宣称数据零损失。

发送命令增加 SPI 参数个数与主/客负载长度检查，避免超长 memcpy 写出 23-word TX 缓冲区。旧版在合成 255-word 命令下可复现 ASan global-buffer-overflow，新版安全返回错误。没有证据证明真实网球发出了该命令，因此不能称花屏根因已修复。

## 诊断

每约五秒的 RFU 统计增加 `ack_ok`、`late_ack`、`max_wait_us`、`rejected_spi`、`staged` 和适配器 `state/com/cmd`。`late_ack` 指成功确认时原模拟重试计时器已经耗尽，不能解释成 IP 重传次数；`max_wait_us` 是累计最大交换等待时间，也不是 Wi-Fi ping RTT。

## 验证边界

13 项实际 RFU 适配器 ASan/UBSan 检查通过，覆盖晚到确认、真实等待边界、有限客机超时、零配置、空交换保留两端数据、越界命令拒绝，以及既有 mailbox/主机驱动发送/ACK 身份保护。14 项真实 gpSP 与生产 TCP/SIO 回归通过。Mac 商业游戏、受控延迟及掌机验证结果另记录；旧花屏会话证据保留。

## Mac 网球比较（2026-10-07）

两个版本各运行两个独立 gpSP 解释器进程，使用相同初始 SRAM 和输入脚本。仅开场 4800 帧加速，RFU 游戏交换开始前切回约 60Hz 实时。脚本和人工测试按键都在本机，不操作掌机。旧版首次游戏配对出现通信错误，随后重试成功；候选首次配对成功，因此两个版本的菜单/选角时刻和角色不同，不能把计数比值作为同负载性能提升比例。

经 localhost TCP proxy 每两秒周期性滞留各方向最多 25ms（保留全部有序字节），约 100 秒的观察中，旧版 `host_no_reply` 从 487 到 1183，候选从 10 到 32；旧版 host mailbox 替换从 192 到 485，候选从 5 到 16。候选成功确认计数从 6804 到 11553，其中 `late_ack` 从 4685 到 7535。均存在误判/替换或调度延迟，不能称零丢包。代理的滞留也不是恒定 RTT、真实丢包或 Brick AP 测试。

两版本均进入比赛，双方截图确认到 Mario 15–0；最终旧版到 30–0，候选到 40–0。候选也从游戏内 Pause Menu 返回比赛。另对候选一个进程停顿约 500ms 后恢复，恢复后双方继续到 40–0，检验暂时调度停顿后的继续运行；这不是 NextUI 菜单暂停/恢复验证。截图、输入、代理统计、等待计数与完整日志保存在私有忽略目录 `build/gba-link/timing-fix/`，商业 ROM 与 SRAM 不进更新包。

本机结果支持部署候选让用户复测，不证明 ARM64 dynarec、真实无线与花屏问题全部解决。候选构建期间两台 SSH 一度超时；恢复后用户确认退出游戏，18:35 已备份部署至两台。实际比赛复测待用户操作，部署记录见 HARDWARE-VALIDATION.md。
